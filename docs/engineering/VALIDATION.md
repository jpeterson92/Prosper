## Evidence model

Distinguish written/structurally checked, implemented, locally verified, independently reviewed, paper accepted, financially authorized and released. Every claim names actual artifact/revision, inputs/environment, scope, results and unresolved/unrun work. Same-agent tests/review do not satisfy required independent tax/model acceptance. Git/source checkpoint, provider evidence, wheel/browser tests and observed investor installation have separate scopes.

Ordinary implementation runs affected checks including upstream/downstream/configuration/schema/child-process/recovery consumers, plus reached lint/type/contracts/package. Explicit commit/sync checkpoints run full Python/package then full frontend. Docs-only work runs the final docs helper. Current-format recovery and material financial/security failures are required; old wire-format parity, migrations, source-code-bound backup compatibility and representation-only proofs are not.

## Proportional verification design

Verification serves a concrete correctness, user-workflow or decision need. Account for agent reasoning/implementation, maintenance, execution and delayed product progress when choosing its scope. In the existing task sketch, name the unresolved question and the cheapest adequate check; this is not a separate document, sizing exercise or approval gate. Reuse current evidence within its actual input/implementation/environment scope. A historical brief's replay/report checklist alone does not justify new tooling or repeated studies.

| Check | Purpose and default placement |
| --- | --- |
| Regression test | Ordinary behavior, independently justified expected results and material failure/recovery cases belong in pytest or the existing browser suite |
| Numerical reference check | Use a separately derived expression or appropriate external implementation when it adds a materially different correctness check. A small test/reference helper usually suffices; outputs copied from the tested implementation are not an oracle |
| Experiment | Use a standalone runner only when its results can resolve a specific open model/product/settings decision. Fix the relevant design before examining evaluation outcomes and report contrary/inconclusive results. Synthetic harness behavior alone cannot decide real model superiority or calibration |
| Workload benchmark | Measure an actual unresolved capacity/latency/memory boundary with declared inputs/environment. Check the reached transport/schema/storage/service path first and label partial/component measurements accordingly |

Choose the smallest useful slice. For example, inspect route/body/source limits and measure a representative full payload before constructing a large simulation to investigate application capacity. Library or service completion cannot stand in for an accepted HTTP/browser workflow. Preserve missing facts, full-union accounting and refusal outcomes; economy does not authorize truncation, economic-limit relaxation or skipped material checks.

Do not create a parallel qualification framework, new serial task or report family merely to label existing work more strongly. Prefer precise names such as reference check, experiment or benchmark. Existing `qualify_*` names need no cosmetic rename; judge their incremental purpose. Their passing status has exactly the scope of the checks performed, with no independent-review, real-data, calibration or financial-use authority implied. A distinct mathematical route authored by the implementing agent remains same-agent evidence.

Keep reporting proportional: one concise result record with the decision-relevant result, actual checks and unresolved limits, plus necessary machine-readable output when useful. Avoid duplicate report transformations, whole-tree identities and byte-identical replay as routine completion conditions. Require stronger artifact identity or replay only for a concrete provenance, nondeterminism, packaging or numerical discrepancy. Preserve historical saved application results without recalculation; test-receipt validity and explicit checkpoint rules remain governed by the helpers and NEXT_STEP.

Expensive model fits/studies run deliberately at the required boundary. Routine tests exercise their essential arithmetic, orchestration and failure behavior using small independently justified cases; reserve full fitting for tests that need it. Do not attach a full-fit fixture to simple profile/shape/rejection tests. Module/session fixture scope is per pytest worker, so it does not by itself prevent repeated expensive setup under parallel execution. [Development](DEVELOPMENT.md#test-receipts-and-caches) owns execution guidance.

For installed-package verification, exercise representative installed code/entry points and any specific dependency, packaging or runtime risk. Replaying a whole unchanged study in the wheel is warranted only when a concrete question requires that scope. Recheck after relevant changes or unresolved failures; preserve required explicit full-verification/checkpoint, financial, security and recovery coverage.
