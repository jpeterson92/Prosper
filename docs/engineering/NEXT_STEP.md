## Quick fit decision and reusable plan

After required intake, use a brief **fits**, **split**, or **blocked** scope/dependency note and reuse the task sketch. No model-capacity comparison, separate sizing report, token/duration forecast or model-settings lookup is required. Prefer completing a coherent outcome with its checks/remediation; split for an actual bottleneck rather than a count of modules or cases.

Use the existing brief, status and focused code/dependency observations to consider one outcome, sufficiently clear semantics, affected boundaries, ready dependencies, meaningful acceptance and room for debugging/review/handoff. These are prompts for judgment, not six separately documented gates. A bounded qualification task can own an unresolved technical dependency. Required financial/data/authority checks still apply.

**Default to execution when a coherent task plausibly fits.** Sizing is a brief screen for clearly oversized work, not a demand for confidence that implementation will be easy. When the evidence is borderline but the outcome is bounded and authority/dependencies are ready, attempt it with internal milestones. Multiple modules, a new schema/lock/registry, sequential internal dependencies, several contracts, or extensive failure cases do not by themselves justify separate invocations. Keep coupled implementation and integration checks together when manageable; do not recursively split merely because more than one substantial engineering step can be named.

**Keep sizing to one brief pass.** Stop when there is enough information for a rough decision. If one specific fact could change that decision, make one focused read-only check of that fact. Do not repeatedly inspect files, write alternative plans, install/probe dependencies or design the implementation merely to prove it fits. Ordinary API details, code discovery and debugging belong to the authorized task. If a concrete consequential unknown remains, name it and take the blocked/qualification branch; if concrete scope remains too broad, split. Do not turn normal implementation uncertainty into an automatic planning-only run. This bounds the process rather than promising an exact number of seconds of internal reasoning.

For a fitting nontrivial task, record **one or two sentences for the fit decision and usually three to five execution bullets in the existing task brief**. Those bullets are both the sizing sketch and the actual coding plan: name the outcome/boundaries, cohesive implementation steps and required verification/review/handoff. Reuse an adequate existing plan rather than rewriting it. A routine small change may need only one sentence; do not create a new planning artifact for formality. Start implementation from this same plan as soon as authority and prerequisites permit. Expand or revise it only for a specific new finding, acceptance need or consequential decision, not because sizing has ended.

Use **fits** when the bounded outcome plausibly looks manageable with its checks. Use **split** only when concrete evidence shows that the combined implementation and verification are too large for one run. In one or two sentences, name the scope bottleneck and why internal milestones would not adequately contain it; naming two boundaries alone is insufficient. Retain each child's own tests. Use **blocked** when required authority, data/rights or consequential semantics are missing and no bounded independent qualification can resolve them. Briefly name the actual reason; no elaborate scoring or proof of predicted capacity is needed. Never weaken financial/release gates to obtain a yes.

**Reassess existing splits locally.** If the next candidate is an unstarted child, consider its immediate unfinished parent under this same threshold. When the remaining children form one coherent task that plausibly fits, select that parent as the one execution unit, retain child IDs/contracts as internal milestones, and update the brief/STATUS pointer before implementation. Dependencies outside the selected parent must be ready; internal prerequisites still execute and verify in order. Do not merge unrelated siblings, climb the whole roadmap, bypass a gate or chain a successor after the selected parent. If the parent is clearly oversized, execute the ready child without another decomposition-only run merely to reaffirm the existing split.

## Select one run mode

| Finding | This invocation does | Required stop |
| --- | --- | --- |
| Quick decision is fits and relevant work is authorized | Reuse the sizing sketch as the execution plan; complete exactly one selected task with checks, review, remediation and handoff | Stop before starting its next sibling or the next phase |
| Concrete scope evidence warrants split and no adequate child plan exists | Decompose and write the plan as described below | Stop after documentation verification, even if the first child now fits |
| An existing split remains necessary and its ready child fits | Reuse the child plan and execute that one child; no planning-only run to restate the split | Stop before its next sibling |
| A dependency or consequential decision blocks the candidate | Identify the exact gap; select a useful independent, fitting qualification/documentation task if available, otherwise request the missing information | No dependent implementation, fabricated evidence or silent policy change |
| User explicitly requested planning only | Inspect, size and prepare/refine the written plan or brief | No application, fixture, executable test or tooling implementation |
| Nothing remains within current authority | Report achieved scope and the specific next decision/gate | Do not manufacture work or broaden release authority |

### Decomposition run

Make only documentation changes. Do not write application skeletons, executable tests/fixtures, install dependencies, initialize Git/tooling, or run child implementation experiments. Read-only inspection needed to understand scope is allowed.

Prefer editing the existing task brief. Create a separate child plan only when the existing document cannot clearly own the split. Preserve the parent ID and add stable child IDs such as `T004.1`, `T004.2`.

For a routine split, the complete default artifact is a one-sentence reason plus a compact table:

| Child / status | Outcome and scope / exclusions | Dependencies | Acceptance and verification |
| --- | --- | --- | --- |
| Stable ID; ready or waiting, with brief fit reason | One useful outcome and its boundaries | Actual prerequisite or owner decision | Concrete expected behavior and checks, linking inherited case IDs |

Link existing source contracts, settings, case derivations and failure requirements; do not transcribe them again. Add only missing facts needed to make the first ready child executable: an unresolved interface, distinct acceptance case or consequential dependency. Dependent children need only enough detail to establish scope and sequence. Several acceptance cases within one cohesive component do not by themselves justify another split. Expand or split further only for concrete scope/ambiguity, not to eliminate ordinary implementation discovery.

Ready means ready to attempt, not verified behavior. Use the established statuses **ready**, **waiting on dependency**, **blocked**, **in progress**, **verified**, or **accepted** with observed support. Keep roadmap updates to changed sequencing/links and STATUS to a short result plus exactly one next candidate. Verify the documentation, rename the conversation and **finish**; no child implementation in this invocation. A routine two-child split does not require a separate execution report, research pass, timing record or new verification harness.

### Execution run

Recheck the ready task against current files/dependencies with the quick fit decision; a prior ready label is not proof that circumstances are unchanged. Reuse the brief and execution sketch that supported the decision, filling only missing material details. Do not restart planning, write a second coding plan or make a separate planning run for a fitting task. Record invocation authority and mode in STATUS, then complete only that task using synthetic data and meaningful checks. Do not skip required verification to stay within an imagined run budget.

If material new evidence shows the remaining implementation and required verification cannot reasonably be completed in this run, stop expanding the implementation. Ordinary complexity or a failing test alone does not trigger this branch; continue routine in-scope discovery, debugging and remediation. Preserve coherent completed work and user changes, record exact partial results and checks, identify a safe remaining slice, and update the plan for the next invocation. Never label partial work complete or conceal unrun checks. The next invocation resumes or remedies that slice before moving to another one.

## Efficient execution defaults

These defaults apply to implementation, planning and configuration work. They govern execution overhead; the quick fit decision, required checks and owner authority still govern scope and correctness.

1. **Read narrowly and reuse context.** Check workspace changes, then use `rg`/headings and bounded sections for the current outcome and its dependencies. 2. **Decide fit once and keep the same plan.** Use the brief quick-sizing decision and execution sketch above, then begin the authorized slice. Do not write six-row tables, duplicate the sketch as a new coding plan, or repeat sizing to obtain more confidence. Reassess only when concrete scope, dependency or semantic evidence changes the decision. Add design detail when implementation actually needs it; do not introduce speculative abstractions, dependencies or adjacent improvements.
3. **Batch implementation and feedback.** Implement a cohesive behavior with its meaningful tests, then run the relevant checks. Fix related findings together before rerunning. Do not invoke a full suite after every small edit. Inspect the diff and review the changed failure paths, provenance, unknowns, exact arithmetic and recovery behavior as applicable; preserve independently justified financial expectations and required independent review.
4. **Use existing checks at the appropriate scope.** Follow the cadence below: meaningful affected checks at completion, full suites at explicit commit/sync checkpoints. For documentation only, finish the content and evidence edits, then run `./scripts/dev.ps1 -Command docs` (text, links, manifest and diff). A successful run needs no identical standalone checker immediately afterward. Rerun for changed inputs or unresolved failures. Review dependency order, authority and concurrent-work preservation directly; do not write custom scripts to assert prose capitalization, word counts or task-ID presence. Additional automation must cover a concrete semantic/behavioral risk the existing checks miss. Financial expectations and independent review remain binding.
5. **Keep one proportional evidence record.** Record material findings, actual commands/results, identity and limitations in the existing brief; a new report is warranted only by substantial evidence. STATUS holds a short current result and one next pointer, with prior handoffs under a separate historical heading. Link contracts and prior evidence instead of copying them into every child. For a routine split, a decision, child table and short check/handoff paragraph suffice. Include detailed failures when they affect correctness, scope, reproducibility or unresolved work; omit repaired prose-check typos and routine command narration. The final reply reports the result, checks/limits and next action without repeating the whole brief.
6. **Escalate process only for evidence.** Use ordinary tool timing; extra timing checkpoints/profiling are optional unless requested or needed to diagnose performance. For small reversible documentation changes, status/diff and focused preservation review suffice; do not build a whole-tree hashing harness by default. Capture stronger preservation identities for interleaved concurrent edits, numerical/reference artifacts or other concrete risk. If process grows without changing a decision or qualifying behavior, stop adding it. No hard time cap, speed guarantee, weakened acceptance or automatic model switch is implied.

Routine authorized debugging, checks and remediation continue autonomously. Ask only for a consequential unresolved decision, missing information or permission actually required by the applicable boundary. Do not ask the owner to reconfirm already authorized routine steps.

## Scaling with project size

The goal is task-sized agent context and review, with broader verification when actual impact requires it. Cheap repository-wide machine checks and deliberate full checkpoints still scale with repository size; do not claim constant total cost or weaken safety to meet a context target.

- **Navigate before loading.** Start from STATUS, the selected brief and the [task navigation map](AGENT_WORKFLOW.md#task-navigation). Search named files/directories or symbols first; expand to the repository only when ownership is unknown or a shared interface changes. Use file-only matches to discover owners, then bounded content reads. Exclude generated assets, lockfiles, runtime state, archives and fixtures from exploratory searches unless they are the subject. Full source/fixture checks still run where required.
- **Follow impact, not every link.** Inspect the changed boundary and its relevant callers, schema/configuration, consumers and failure/recovery paths. A link is navigation, not an instruction to read its entire subtree. Broaden for shared exact arithmetic, storage/schema, API contracts, dependency/build settings, financial semantics or uncertain coverage; explain the concrete reason. Do not infer isolation from directory names alone.
- **Bound durable intake.** Keep AGENTS as policy/navigation, not a running changelog. STATUS holds current authority/result, one next candidate, active blockers and links; aim for one or two readable pages (roughly 1,500 words or less). On growth, move superseded narrative verbatim to dated history, preserving locators and current unresolved obligations. Do not append each task's full report or test transcript to STATUS. History files are consulted for a specific dependency and are never mandatory intake.
- **Maintain the touched knowledge only.** Update the owning brief, compact STATUS and any contract/map entry whose meaning changed. Do not reconcile all task statuses, roadmap counts, decisions or historical evidence on every task. Add a local AGENTS file or reusable skill only after a repeated area-specific need; link to shared policy rather than cloning it. The navigation map lists subsystem entry points, not every module/test.
- **Scope review and selection.** Review the task delta against intake, preserving pre-existing edits; separate unrelated findings into a short follow-up rather than repairing the project. Reuse qualified, unchanged references with their exact scope. Keep affected tests plus consumers and explicit cold-baseline selections; retain full checkpoint/CI and independent-review obligations. No automatic dependency refresh, environment rebuild, wheel probe, browser sweep or new agent is justified solely by a larger repository.
- **Control caches and growth by evidence.** Existing testmon, Ruff/mypy and tool caches are the default. Do not replace content identities with timestamps/Git status alone, skip untracked inputs or build a new index/selector because future growth is possible. Cache pure repeated work within one invocation where safe; persistent caches need complete invalidation and failure tests. Profile a concrete bottleneck before adding orchestration. Keep large raw outputs in ignored evidence and return only decision-relevant summaries to context.
