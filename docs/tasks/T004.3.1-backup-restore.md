## Implemented behavior and acceptance evidence

**Implemented and locally verified.** [recovery.py](../../src/prosper/recovery.py) supplies `backup` and `restore` with closed, strict, versioned manifests. SQLite's backup API captures the database; only references in that snapshot determine the required evidence. Complete original bytes accompany inactive checkpoints, every preview lifecycle, active history and all command outcomes. Verification uses database integrity/schema checks plus the existing reconstruction/history/receipt logic, with additional complete-reference and receipt-generation checks. No schema or dependency changed.

The manifest includes application/schema versions, an actual implementation fingerprint (package Python sources, installed runtime dependency versions and Python major/minor), a bounded caller-supplied candidate label, database/evidence hashes and byte lengths, state counts and active generation. Candidate labels are assertions, not independently verified Git identity; hashes do not authenticate an untrusted backup. Restores require the current application version/fingerprint/schema. No old backup migration occurs. The engineering envelope is 512 MiB per database, 10,000 required evidence objects within existing evidence byte limits, and an 8 MiB manifest; no performance capacity is claimed.

Destinations are guarded and reserved exclusively, including refusal of preexisting empty directories. Backup publishes the manifest last. Restore first copies into `restore-work`, verifies all copied state, publishes evidence then the database without replacing an existing file, and clears `restore-in-progress` last. The small [storage guard](../../src/prosper/persistence.py) rejects any runtime retaining that marker. An interruption between database link/unlink also leaves a multiply linked non-ready database. Failed files remain for the next component; successful restore leaves an empty work directory. No cleanup or marker-based repair is implemented.
