## Implementation and evidence

**Implemented and locally verified.** [evidence.py](../../src/prosper/evidence.py) provides `RuntimeBoundary`, `EvidenceReceipt`, `EvidenceStore` and safe coded `EvidenceError` failures. [43 filesystem cases](../../tests/test_evidence.py) exercise this boundary. There are no new dependencies or changes to financial calculations, fixtures, parser/schema, lockfile or build configuration. Synthetic scratch only; no actual per-user investor directory or real data was accessed. No database, account/broker operations, push, merge or release occurred.

Receipts use `evidence-bytes-v1`, raw SHA-256, byte length and an exact hash-derived relative reference. Original bytes remain distinct from parser canonical identity; differently formatted equivalent F001 inputs retain separate raw objects. Reopening uses no in-memory state. Retrieval requires a regular single-link file, the existing 2 MiB parser bound, exact length and matching hash. A stored object cannot be replaced through the adapter; missing/changed/truncated/oversized/incompatible objects fail without trusted bytes or invented values. The adapter stores bounded bytes, including diagnostic evidence that is not a valid bundle; parsing/inspection remains a separate gate.

Runtime/source roots and mode are explicit trusted caller configuration. Synthetic mode permits only children of source `.local`; private mode rejects source descendants/ancestors and accepts a separate ordinary local directory. Private-mode tests use fictional bytes in isolated synthetic scratch, not actual private state. Paths are absolute local filesystem paths; unsafe components, traversal, reserved/device names and all detected symlink/junction/reparse aliases are rejected. Existing ancestors and adapter-owned paths are rechecked during operations. Tests actually created both Windows junctions and symlinks on this host, including aliases introduced after the adapter opened; neither case was skipped. File hard-link aliases are rejected by retrieval.

Publication writes exclusively to a UUID staging filename, flushes/fsyncs and closes it, checks its bytes, creates a same-volume hard link at the final name, and unlinks that operation's staging name. The real Windows primitive was exercised for successful publication and existing-destination rejection, alongside injected write/publication failures. Existing corrupt objects are preserved and rejected. Verified duplicate publication returns the existing object; a simulated competing complete publisher is checked before success. Failures leave the earlier complete object readable. If interrupted after linking but before unlinking staging, both complete names may remain; the adapter returns no receipt and rejects the multiple-link object on reopen/retry. Recovery must explicitly resolve it before a future database can trust it.

This mechanism uses Python's documented [hard-link operation](https://docs.python.org/3.12/library/os.html#os.link) and Windows [reparse-point attribute](https://docs.python.org/3.12/library/stat.html#stat.FILE_ATTRIBUTE_REPARSE_POINT); the observed results come from this host's tests, not documentation alone. Unsupported filesystem/link behavior fails without a copying fallback. No automatic orphan cleanup or complete restore is implemented. Hashes establish byte identity, not authenticity; API immutability does not stop external edits, which reads detect. Path checks assume no hostile process swaps directory components concurrently. No ACL/encryption or power-loss durability guarantee is claimed; fsync plus local tests do not establish durable directory publication across power loss.
