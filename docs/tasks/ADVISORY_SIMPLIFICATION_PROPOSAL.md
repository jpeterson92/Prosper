## Recommended product

Prosper should help an investor import current holdings and lots, inspect estimated loss opportunities and benchmark risk, compare a small set of constrained suggestions, and export a manual trade worksheet. The investor reviews and executes at the broker. For another analysis after trading, import a fresh holdings/lot snapshot rather than have Prosper reconstruct the account from fills.

The application should be accurate enough to support the stated estimates, transparent about assumptions and missing inputs, and easy to refresh and recover. The design standard is: **a control earns its place by preventing a material recommendation error, preserving user work, protecting private data, or making a suggestion understandable.** Source spelling, proof completeness and internal lifecycle purity are not user outcomes by themselves.

Retain the accepted equity-only modeled scope, selected cash/final-cash distinctions, zero-positive-gain objective constraints, whole-share proposed orders, chosen benchmark route, and accepted DCC/industry risk direction. Changing those financial/product choices is a separate decision. Simplifying infrastructure does not require replacing the risk methodology, relaxing economic limits, or pretending incomplete data is complete.

The first advisory release should stop at saved/exported suggestions and refresh/reanalysis. Execution commitments, fill reconciliation, account reconstruction, automatic basis maintenance and forward monitoring should be deferred as product features. A worksheet can carry review reminders about later activity; reminders do not constitute monitoring or clearance.

## Numerical policy to adopt

Prefer Polars for tables and NumPy/SciPy for numerical work. Use Float64 for derived market values, weights, returns, exposures, risk, optimization and estimated losses/costs. Retain supplied quantities and basis as decimal strings or ordinary Decimal at import and the final trade-check boundary. One small conversion/rounding module is sufficient; this is not a new numeric framework.

| Topic | Proposed rule |
| --- | --- |
| Input representation | Retain the original source file. Parse supported formats consistently, accepting economically equivalent spellings/notation through the adapter. Validate type, units, finiteness and plausible magnitude; maintain byte/row/field-length limits. Do not reject usable data merely because it exceeds a universal 12-place fractional rule. |
| Precision | Full available Float64 precision for analytics; ordinary explicitly configured Decimal precision where it is actually needed. No arbitrary rational representation or 80-digit universal calculation requirement. Any actual overflow/nonfinite result remains an error. |
| Aggregation | Use native column operations and ordinary numerical summation. Check missing/nonfinite values and membership before accepting a total; do not let null-skipping produce a purported complete portfolio. |
| Weight sums | Check derived normalized weights against one with a documented numerical tolerance. Never silently repair a source membership/coverage error by renormalizing. D045's explicit retained-equity value normalization stays intentional. |
| Comparisons | Separate floating-point error tolerances, solver feasibility tolerances, source reconciliation differences and investor economic limits. No universal epsilon and no blanket penny allowance across all checks. Record/test tolerances in the calculation that uses them. |
| Discrete trades | Identify the exact source lot and security, propose whole shares under the existing policy, and verify quantities against the imported holding using a simple decimal/integer comparison. Preserve fractional residual holdings. Numerical tolerance cannot permit selling an unavailable share. |
| Near a boundary | Recheck the final suggested orders independently of candidate construction. Use the small decimal boundary or a conservative review outcome where rounding could flip an estimated gain/loss, cash availability or a hard limit. Never use a float tolerance as permission for an economic policy violation. |
| Display | Estimated USD amounts normally to cents; prices/share quantities show enough precision for review; weights and risk use readable percentages/basis points appropriate to their uncertainty. Display rounding never changes share quantities. Include the valuation date and estimated nature, rather than displaying misleading digits. |
| Reproducibility | Same inputs/settings/version should give stable materially equivalent outcomes under declared tolerances and deterministic selection rules. Bit-identical floating results across platforms/library versions are not a product guarantee. Save the output itself so historical viewing does not depend on recomputing it. |

A derived weight of approximately 0.6666666666666666 is acceptable; it need not travel as 2/3. A proposed sale of a lot with unknown basis is still unable to support a calculated loss. These are different concerns. Implementation must choose and test tolerances against supported scale, including values near zero; exact constants are not adopted by this proposal.

The Python documentation provides ordinary [relative/absolute comparison tolerances](https://docs.python.org/3.12/library/math.html#math.isclose) and [rounded Decimal arithmetic](https://docs.python.org/3.12/library/decimal.html). These are mechanisms, not evidence for a particular investment tolerance. No tax-law change or interpretation is proposed here.

## Audit, explanation and saved data

Replace the notion of a universal evidence system with a small set of user-owned records:

1. **Import:** source name/type, as-of/import times, retained bytes or a durable copy, source ID/checksum, normalized rows and relevant row errors. A failed replacement import leaves the prior selected snapshot intact. Keep account details private; a checksum does not anonymize them.
2. **Analysis:** imported snapshot ID, selected benchmark/history/taxonomy/settings, calculation version, input data actually used, results, exclusions and warnings. Pin only the history window/data needed by saved analyses; do not retain every refresh forever by default.
3. **Suggestion/export:** suggested lots/securities/sides/quantities, indicative prices and costs, estimated loss/risk/cash, assumptions and creation/data dates. Store the reviewed/exported result as a historical artifact, not an executable order or claim that anything filled.

Use one run-level input/output bundle rather than independently registered proof objects for every intermediate. Source identifiers are useful; cryptographic chains, multiple overlapping hashes and field-by-field provenance are optional tools only where they answer a concrete question. Normal logs should report operations/errors with IDs and counts, not portfolio contents. Diagnostics exports remain private and opt-in.

Deleting a saved analysis should release its retained inputs when no other saved analysis needs them. Losing rebuildable cache entries should cause a refetch/rebuild or an explicit unavailable result, not make unrelated saved reports unreadable. Deletion of source data/analyses must be user-visible; no automatic destructive cleanup is part of this proposal's implementation authority.

## Proposed application structure

Keep the existing React/TypeScript UI, FastAPI/Pydantic contracts, Python domain logic, Polars analytical tables, NumPy/SciPy calculations and SQLite. No new service, task framework, ORM, message bus or proof abstraction is required to simplify the project.

The conceptual flow is `import -> validate inputs -> analyze -> validate final suggestion -> save/export`. Keep four practical areas: import adapters, calculations, application/storage services and UI. Avoid creating packages just to match this diagram. Pydantic validates transport/import shape; Polars handles tables; explicit domain checks enforce material recommendation conditions. Do not repeat the same checks in every layer without a reason.

Use a single application writer and SQLite transactions for authoritative changes. Keep long calculations outside write transactions. Tag a calculation with its input revision and settings: late results must not replace the current result. Prefer rejecting a second concurrent run initially to building distributed command/idempotency/cancellation machinery; retain responsiveness and an honest running/failed/completed status. UI retries still must not duplicate an import or replace newer work.

Use SQLite's [backup facility](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup) for database consistency. A normal backup/export includes retained source/run records and any authoritative external files; do not copy a live database unsafely or assume database-only backup covers external files. Keep rebuildable caches outside the required backup set. Qualify one interruption/restore path and schema compatibility rather than maintain separate synthetic and real product recovery architectures.

Tests may inject fictional providers and temporary directories. Synthetic fixtures and real private local use should share the same calculation code; a fictional-data label is not a second application lifecycle. Existing prohibitions on accessing/transmitting real account data without explicit authority remain unchanged.

## Useful boundaries and unnecessary barriers

| Keep | Simplify or defer |
| --- | --- |
| Missing basis/quantity/security blocks affected sale calculations; missing required risk data blocks a risk-constrained suggestion | Global refusal to show otherwise useful imported holdings, loss diagnostics or explicitly partial exposures |
| Explicit cash budget and instrument/currency scope; independent final checks for sell quantities, cash, costs and economic limits | Broker settlement simulation, reservations and submission holds when the product does not track orders |
| Dates/units, duplicate detection, security/session alignment, corporate-action and adjustment consistency | A proof record for every intermediate observation or perpetual reconstruction of all known-at histories |
| Unknown industry remains an unknown bucket with affected limits unavailable | Treating a missing label as zero exposure or demanding complete classifications just to display other diagnostics |
| Source as-of and freshness warnings; refresh before a new suggestion after external trades | Treating old exports as current, or trying to guarantee execution state through a local saved plan |
| Loopback/origin/session protections, input limits, safe file paths, transactional writes, export escaping and private local storage | Adversarial filesystem/proof machinery whose only purpose disappears when storage is consolidated; any removal needs a focused security review |
| Complete coverage for the actual modeled universe under the chosen model | Requiring every excluded source instrument's history/classification or proving all holdings of every possible benchmark before an unrelated diagnostic |

For example: missing basis on one lot should exclude that lot from harvest estimation while showing its holding; missing benchmark history may allow holdings/loss inspection but must not produce a validated tracking-error result. An exported worksheet should say it is a dated estimate; a historical view should remain readable after an application update.

## Model ambition, testing and project governance

The accepted DCC/industry model is itself substantial work. It is a separate source of scope, not something that removing hashes or decimal traps solves. Keep its accepted implementation direction and focused parity/calibration work. A simpler risk model, narrower asset scope or relaxed risk constraints would need an explicit separate proposal; do not slip them into this cleanup.

Keep meaningful independent expected examples, boundary/failure tests and a final suggestion validator that does not reuse the optimizer's constraint-building logic. The validator can share basic types/numeric helpers. Concentrate tests on wrong-lot/oversell errors, missing basis, double-counting, loss sign, cash/cost handling, data alignment, risk calculations, stale results and recovery of user work. Retire tests whose sole purpose is an intentionally removed representation/proof guarantee, after replacement tests establish the retained behavior. A reduction in test count is not itself success.

Keep affected checks during development and full checks at the established commit/sync cadence. Keep a focused package/install smoke and actual release checks. Move effort from repeated narrative proof and identical-output hashes toward realistic end-to-end synthetic scenarios and a small observed manual workflow before claims of investor usability. Independent tax/model review remains necessary for the applicable real-use claims; it should not block unrelated internal synthetic feature development. Claim-specific prerequisites stay honest and visible.

Documentation should consist of concise agent policy, current product/architecture/numeric contracts, one live next-task handoff and decision records for consequential changes. Git/CI identify ordinary engineering revisions. Archive completed detailed task reports; stop reproducing their evidence in multiple current documents. A short exception note suffices when Python fits better than Polars. A new storage abstraction or control needs a named user failure and a reason existing tools are insufficient.
