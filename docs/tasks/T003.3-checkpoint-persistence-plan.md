## T003.3.1: Immutable evidence and runtime boundary

**Status: verified locally — [execution evidence](T003.3.1-immutable-evidence.md).** The brief below retains original scope/acceptance.

**Outcome:** a caller can publish bounded original bundle bytes into an explicitly selected synthetic runtime, close/reopen the adapter and retrieve exactly those bytes by verified identity. Publication never replaces an existing different file or returns a success receipt for incomplete/corrupt evidence. This is evidence storage, not a committed portfolio import.

**Included scope and boundaries:** one narrow runtime-path/evidence adapter, typed immutable receipt, synthetic filesystem integration tests and developer documentation. Use the standard library where sufficient; do not add dependencies speculatively. Define a storage-format version and a receipt containing raw SHA-256 and byte length, with an adapter-controlled relative reference. Derive final evidence names from validated hashes, never imported IDs, filenames or arbitrary path text. Canonical identity remains available from the parser and is not conflated with raw-file identity.

**Runtime policy:** require an explicit runtime root and mode; qualify private mode outside a supplied source boundary and synthetic development mode under a designated ignored `.local` subtree. Do not create default per-user state in this slice. Resolve paths before writes; reject source-root/ancestor overlap in private mode, traversal/absolute evidence references, and symlink/junction/reparse aliases that escape the permitted root or redirect it into source. Validate relevant existing ancestors and adapter-owned children before publication/read. Reject unsupported redirection safely rather than silently following it. Test private-mode separation with a synthetic source tree and a separate synthetic runtime under pytest scratch, never actual investor data. A static path check is not a claim of protection against a hostile process replacing directories concurrently; record the exercised local threat boundary.

**Publication/read contract:** accept bytes within the parser's existing byte bound and compute identity from those bytes. Store original evidence without normalizing it. Write staging content exclusively, finish/close it, then publish without replacing an existing destination. Qualify the chosen standard-library mechanism on the actual Windows filesystem and report its interruption/durability limits. Successful repeated publication verifies and returns the existing byte-identical object. An existing different/corrupt object, invalid reference, size/hash mismatch or missing object fails explicitly without overwriting or returning trusted bytes. Reopening the adapter requires no in-memory publication state. No database, import receipt/idempotency command, active generation, correction acceptance or orphan cleanup exists here.

**Concrete acceptance and method:**

1. Publish F000 and F001 bytes to ignored synthetic scratch; reopen the adapter and compare returned bytes, independently computed SHA-256 and byte counts. Parse retrieved F001 and confirm the existing canonical identity and source decimal spelling/quantum are unchanged. Use the existing fixtures rather than new financial assumptions.
2. Publish identical bytes twice and verify the same complete object/reference. Publish differently formatted but canonically equivalent F001 bytes and retain distinct raw identities with equal parser canonical identity. Read the first object again unchanged.
3. Inject a staging write failure and a final-publication failure using a narrow filesystem seam. Neither returns a success receipt or exposes a partial final object; a prior complete object remains readable. Exercise the real publication primitive in successful tests, not only mocks. Preserve/report any staging artifact; no broad recursive cleanup routine.
4. Precreate corrupt evidence at the derived destination; publication and verified retrieval fail without replacing it. Missing, truncated, changed and oversized files fail bounded reads. Empty/invalid digest, traversal and absolute references are rejected before arbitrary filesystem access. Error text excludes supplied payloads.
5. Exercise private/source overlap and source-relative synthetic acceptance, sibling-path prefix confusion, existing files where directories are expected, and supported Windows symlink/junction/reparse alias cases. Record any OS privilege or filesystem limitation explicitly; do not count skipped alias cases as passes. Verify generated integration files are ignored by Git. Do not probe unrelated user directories.
6. Run the project helper check and package commands, review write/read boundaries and failure ordering, remediate findings, refresh authored checks/manifest and report exact local revision. These checks qualify this adapter only; no database or financial-use result is implied.

**Fit assessment:** one outcome **pass** (immutable input evidence); understood semantics **pass** (byte identity, explicit root/mode and fail-closed reads); bounded changes **pass** (one filesystem boundary and its tests, with no SQLite); ready dependencies **pass** (existing bytes/hash/parser/toolchain); executable acceptance **pass** (real synthetic filesystem round trips and injected failures); completion margin **pass** for a conservative attempt because database schema/transactions and application recovery are excluded. Reassess Windows publication/path behavior before implementation; if a newly required platform mechanism materially expands scope, preserve the gap rather than claim untested guarantees.

Fresh sizing must inspect these actual contracts and the minimal schema; this status does not authorize chaining from the T003.3.1 build.

**Outcome:** a validated synthetic checkpoint can be appended as an immutable version, then loaded after SQLite close/reopen with exact canonical values, explicit unknown reasons, original source evidence and both identity hashes intact. Earlier versions remain queryable. Persisted inspection does not activate an import or make it planning-ready.

**Included scope and boundaries:** one versioned SQLite adapter and integration tests consuming T003.3.1's verified receipt/read interface. Use the adopted SQLite backend through Python's standard library; record actual SQLite version/capabilities. Establish a minimal fresh schema/version marker, explicit transactions and rejection of unknown/incompatible schema versions without silently migrating or rewriting them. No general migration framework, ORM, analytical store, active checkpoint switch, import command/generation/idempotency service, API or UI.

Use the minimum representation satisfying the parent contract. A canonical document stored as TEXT with decimal strings and explicit null/reason pairs is permissible; conceptual records do not require a table each. Whichever representation is chosen, tests must observe SQL storage types of the actual authoritative values, not only compare an in-memory reconstruction. Do not use SQL numeric arithmetic/coercion for exact book values. Retain original source bytes through their evidence reference; loading canonical data alone must not silently replace original text/quantum. Record source cutoff/effective time separately from the actual append recorded time, and schema/semantics/canonicalization/storage versions, source identity, raw/canonical hashes and receipt length/reference.

Revalidate parser identity and inspection eligibility at the persistence boundary rather than trusting a manually fabricated public dataclass or mismatched receipt. Incomplete-but-inspection-valid F004/F009 facts may persist with reasons; contradictory/unvalidated data cannot be represented as a validated checkpoint. New source versions append without overwriting prior rows/evidence. Duplicate storage behavior must be explicit and preserve existing rows; this does not implement import-command idempotency or accept source corrections. Reads verify referenced evidence and stored identity/metadata consistency before returning a trusted checkpoint; missing/corrupt/incompatible state fails with a specific non-ready error and no invented values.

**Concrete acceptance and method:** F000/F001 survive a new connection and adapter instance; F001 still inspects to 12 FAAA/5 FBBB, settled cash `319`, settled-cash NAV `2399`, basis `2181` and planning-ready false. Separately round-trip parser-valid synthetic fractional, 28-significant-digit/12-fractional-digit limits, signed cash movement, redundant source zeros, zero and explicit unknown basis/coverage; compare original text/quantum, canonical strings and null reasons. Extreme values need not produce a supported derived aggregate: preserve inspection's located unknown result rather than round it to fit. Observe `typeof` for stored book fields (and JSON extraction if used) to demonstrate TEXT, with null plus a separate reason for unknowns. Reopen and query at least two retained versions with distinct recorded times and unchanged source effective time where applicable.

Exercise real SQLite transaction rollback with failure after an insert but before commit, failed evidence publication before inserts, wrong/fabricated evidence receipt, incompatible schema, malformed stored payload and missing/changed referenced evidence after close. No failed append can leave a partial checkpoint/reference set, and a prior stored version must remain readable. Evidence published before a failed transaction may remain unreferenced; record this without calling it complete recovery. Reuse T003.3.1's runtime rules for both database and evidence locations and test redirection of the database filename/sidecars within that boundary. Run full helper check/package, same-agent review/remediation, authored verification and exact-revision handoff. Qualify only the storage portion of V25/V38/V44; T004.2 owns import state/idempotency/concurrency and T004.3 owns backup/restore.
