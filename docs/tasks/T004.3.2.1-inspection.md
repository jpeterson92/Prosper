## Implemented contract and acceptance

**Implemented and locally verified.** [inspection.py](../../src/prosper/inspection.py) supplies `inspect_recovery(boundary, role)` for explicit caller-selected `runtime`, `backup` and `interrupted_restore` roles. Immutable reports contain status, safe relative findings, database observations, a deterministic fingerprint of rows within the read snapshot, distinct required receipts, optional fully reverified state counts/generation and file length/hash/identity/link classifications. `verified` describes the artifact at the observed snapshot, never financial readiness; `planning_ready` stays false. Reports are not mutation capabilities.

The inspector inventories only bounded known layouts, preserves unknown files and refuses arbitrary directory/reparse traversal. Schema-three references and complete application rows are verified on one read-only SQLite transaction. Missing/empty/foreign/incompatible/corrupt databases are never initialized or upgraded. Constructor-free `EvidenceStore.existing`/`CheckpointStore.existing` and extracted connection-level verification helpers reuse existing exact/source/history/receipt semantics. Original backup/restore still uses the same verifier; no schema, dependency, financial policy or file publication behavior changed.

Required objects, valid unreferenced objects, standalone staging, local publication aliases and unexplained links are distinct. A local alias observation requires nonzero inode identity, matching bytes and content address, the complete observed local link count, known object/staging layout and compatible required length. It stays non-ready and is not repaired. Extra/external links or contradictory receipt lengths remain unresolved. A standalone staging file has no inferred intended length/digest or import acceptance. Backup manifests must agree with copied files, exact current implementation identity, full reference set and state. Legacy restore markers/work are unbound and retained; known empty work from completed restore is harmless.

Read-only SQL may still create SQLite sidecars or change reader locks in `-shm`. Shared-memory content is classified as engine coordination and has no authoritative content hash; its path/type/link/identity/size guards remain. Cold sidecar creation can yield `inventory_changed`; repeat inspection after creation is stable. Actual concurrent WAL commits produce a coherent earlier snapshot with explicit change findings. Hot-journal reads requiring rollback fail non-ready without changing the journal or database. No database, evidence or manifest payload repair/deletion/rename/initialization occurred in the inspector.

Engineering limits: 25,000 enumerated entries, 1 GiB cumulative observed file lengths, 50,000 application rows and existing per-file bounds (512 MiB DB, 8 MiB manifest, bounded original evidence). These bound work and reject excess; target scale/performance is unmeasured. Hashes are integrity checks, not authentication; no hostile concurrent path-replacement, ACL isolation or power-loss guarantee is claimed.
