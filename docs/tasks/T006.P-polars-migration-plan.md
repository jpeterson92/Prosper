## Table and arithmetic rules

- Construct tables from already parsed, bounded records with explicit schemas, including empty/all-null inputs. Keep raw strings, JSON token kind, source/row hashes, section/index, stable security IDs, dates, evidence locators, unknown reasons and dispositions. Do not replace the lossless parser with inferred CSV/JSON reads.
- Preserve stable source/universe/session ordinals and explicitly restore each consumer's existing order after joins/grouping. Existing history coverage uses security/session order while risk assembly uses session/security order; do not impose one global order. Preserve located issue ordering as part of the observable result.
- Validate uniqueness/cardinality before a join can multiply rows. Match source decisions by full locator/context, identities by qualified stable IDs, and history by full selected context/security/session. Never infer identity from ticker or value equality. Null keys remain unresolved; do not make missing IDs match each other.
- Carry unknown reasons and completeness flags alongside values. Missing/invalid known facts cannot become zero, a dropped row, a successful empty aggregate or a qualified partial total. A zero for a security absent from one side is allowed only after complete membership/identity qualification proves that absence under the existing contract.
- Retain Fraction-based exact arithmetic for money/quantities/NAV, ratios and exposure sums where required. Tables can carry exact strings or numerator/denominator strings and group membership; perform exact reductions over those groups in Python. Do not use Object columns or row-wise Python UDFs as a substitute for the intended joins/expressions. Native decimal/integer calculations may replace an exact operation only with proven precision/scale/overflow bounds and equivalent results; that optimization is not required by this plan.
- Keep Float64 conversion at the existing qualified analytical boundary; reject non-finite/missing numerical inputs before NumPy consumers. Keep exact values authoritative for equality, completeness and limits.
- Do not change public API schemas, authoritative storage formats or add a second persisted source of truth. Defer new Parquet snapshots until an actual consumer needs them, with provenance/schema/retention/recovery qualification in that owning task. In-memory Polars use does not require a Parquet migration.

The official [join guide](https://docs.pola.rs/user-guide/transformations/joins/) supports the proposed matching operations. The [missing-data guide](https://docs.pola.rs/user-guide/expressions/missing-data/) documents null/NaN distinctions and aggregation behavior that require explicit completeness checks. [Data types](https://docs.pola.rs/user-guide/concepts/data-types-and-structures/) and [installation](https://docs.pola.rs/user-guide/installation/) are implementation references; they do not establish Prosper's pinned-version compatibility.
