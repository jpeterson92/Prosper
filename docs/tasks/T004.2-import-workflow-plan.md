## T004.2.2: Atomic activation and command receipts

**Outcome:** a commit command either publishes one coherent active checkpoint/generation and durable outcome receipt, or leaves prior active state intact. Reopening and retrying cannot duplicate holdings/events or accept a stale distinct command. This child owns all commit atomicity and its own failure/concurrency checks.

**Included scope and boundaries:** build on verified staging, with minimal active-state/generation and mutation-receipt records in the same database. Refactor only the checkpoint transaction boundary needed to validate/insert/read a checkpoint within the application's transaction; do not call an independently committing append and then switch active state in another transaction. Preserve existing immutable append/read behavior. Serialize authoritative writes with real SQLite transactions, reread reviewed evidence and source conflicts under the write boundary, and commit checkpoint reference, preview transition, generation and receipt atomically. An initial empty runtime has generation zero; each genuinely new active import advances it once. Current inspection reconstructs the active immutable checkpoint with its actual generation/readiness; empty or corrupt state is explicit.

Bound this synthetic workflow to the reviewed profile/traded-account identity. A different identity cannot silently replace that portfolio; report review-required. Do not implement account switching or automatic correction acceptance. Compare recurring source activity against previously committed evidence, not just the current snapshot; rejected/staged inputs do not establish accepted events. At minimum namespace source event identity by profile, source ID and account ID plus event ID, with source-version changes unable to bypass conflict checks. Normalize using the existing versioned event representation, retaining original evidence and distinguishing exact equivalence from changed event content. Cross-checkpoint changed quantity, fee or other event content is F005 conflict/review-required; never overwrite or merge. Omitted historical events are not implicitly deleted. Source-format/identity ambiguity remains review-required.

Define bounded scoped command keys and a versioned payload hash that includes operation, preview/evidence identity and expected generation. Same scoped key/same payload returns its recorded outcome even after later commits; same key/different payload fails. Check existing receipts before stale-generation rejection so a successful retry remains successful. A distinct command must pass the current expected-generation check before any active mutation. Exact previously committed raw imports return/reference the prior import without advancing generation or restoring historical active state; document and test how this no-op is receipted. Never let duplicate identity bypass same-key/different-payload rejection. Store deterministic business outcomes consistently; transient storage/evidence failure must not leave a success receipt. Clearly distinguish the receipt's original outcome/generation from a separate current-state inspection.

**Acceptance and verification:** F001 commits once, repeat preserves quantities/cash and generation; F002/F003/F006 and rejected previews cannot replace the valid active state. F004/F009 can commit reconciled incomplete facts and retain financial blocks. F005 retains both evidence versions and reports a source conflict without merging; same event content across successive snapshots is permitted. Test conflict against an older committed version, source/account scoping and changed source version. Reimport an older committed checkpoint after a newer one and retry an old successful command: neither rolls active state back.

For F007 inject failure after actual writes and before commit, then reopen in a new process: checkpoint/active generation/preview/receipts remain coherent, and a retry can finish once. Test missing/corrupt staged/committed evidence without silent repair or a clean current-state claim. For F008 use two distinct valid previews/commands with the same expected generation and actual competing SQLite connections/processes: one wins, the other returns stale/review-required. Same-key concurrent/restart retries return one durable outcome; changed-payload reuse fails. Do not replace these checks with mocks. Preserve all T004.2.1 behavior, full local check/package and installed-process qualification, with review of transaction/receipt ordering and failure paths. No tax correctness, independent review, UI/HTTP or complete recovery claim is established.

**Conditional fit:** one atomic result, known semantics and executable acceptance **pass**. Bounded changes and completion margin are credible only after T004.2.1's actual service/schema are verified; ready dependencies currently **wait**. Reassess before executing. Keep transactional success, retries, conflicts and concurrency together, rather than splitting off evidence required for a safe commit. No general correction engine, broker format, account manager or future-plan approval/reservation state is included.
