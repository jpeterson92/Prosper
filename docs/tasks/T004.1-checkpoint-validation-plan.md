### Parser bounds and diagnostics

The following are planned engineering resource limits for this child, unrelated to financial policy or measured portfolio capacity. Exercise exact-limit and over-limit cases; if the actual schema needs a different engineering bound, record the reason and tests without changing accepted financial limits.

| Resource | Initial bound / required handling |
| --- | --- |
| Byte payload | At most 2 MiB; reject before decoding oversized input; one complete UTF-8 object, no BOM, trailing document or nonfinite JSON extensions |
| Container depth | At most 16, root object counted as depth 1; enforce before unbounded recursive model decoding, respecting strings/escapes |
| Records | At most 10,000 across top-level record arrays and at most 10,000 elements in any array; never truncate |
| Text | IDs at most 128 characters; other individual strings at most 4,096; exact fields retain T003.2's stricter bounds; reject invalid Unicode scalar strings rather than failing during fingerprint encoding |
| Diagnostics | At most 100 returned issues, with an explicit further-issues indication if needed; no full payload/value echoes or raw traceback as a user diagnostic |

Detect duplicate object keys at every nesting level before a mapping/model can overwrite them. Reject duplicate record IDs/composite identities within their defined family rather than merging records. Unexpected fields, wrong types, unknown schema/semantics versions, false/missing fictional-data flag and numeric JSON tokens in exact fields fail without coercion; no JSON number is first converted through binary float. Reject malformed ID/date/offset strings. A well-formed reference to a nonexistent record is deliberately deferred to T004.1.2, not treated as resolved here.

Diagnostics include a stable code and field/record path (or byte/text offset for undecodable syntax). Treat imported strings as inert data. No evaluation, template/formula execution, path dereference, network lookup or payload logging belongs in the parser. Later UI escaping remains a separate obligation.

### Evidence and normalized identity

Normalized identity includes schema, semantics and canonicalization versions; all meaningful fields, IDs, explicit unknown reasons, inclusion references, and explicit basis quantum remain represented. Canonicalize exact numeric values with T003.2. Canonical field names/order and record-family ordering must be deterministic; sort records by unique stable ID or a documented composite key, and inclusion references by unique ID. Do not sort an order-bearing field without an explicit semantic reason. Preserve distinct source events even when their other fields match.

Numeric source spellings/inferred decimal precision remain available in source metadata/raw evidence. The normalized identity may equate `12.0` and `12.00` when explicit semantic quantities/quantum and every other field agree; that never discards either evidence version. A changed basis quantum, unknown reason, source/event identity or financial fact changes normalized identity. Local observation time, decoder diagnostic order and object memory identity cannot change normalized identity. Specify exact UTF-8 JSON encoding and exclusions in the implementation evidence; do not fingerprint Pydantic reprs or platform-dependent object dumps. Neither hash proves authenticity, permits financial use or implements import idempotency/correction handling.
