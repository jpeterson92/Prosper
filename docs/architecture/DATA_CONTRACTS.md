# Data-contract framework

Current advisory contract under [D046/ADR-0012](decisions/0012-adopt-proportional-advisory-scope.md) and [D047/ADR-0013](decisions/0013-adopt-unreleased-clean-break-development.md). No backward compatibility with unreleased Prosper implementations is required. These are implementation requirements for T019.2-.6, not claims that current legacy schemas already implement them. The [numerical contract](../engineering/ADVISORY_NUMERICS.md) owns representations/tolerances; [STATUS](../STATUS.md) owns actual evidence.

## Shared conventions

Use the minimum records needed to import a current snapshot, calculate estimates and save/explain a suggestion. Preserve original sources once, material values/units, stable account/security/lot references and useful row locators. Unknown is null with a reason, never zero. Numeric spellings need not remain distinct after normalization; original files remain available. Missing classification or basis blocks its dependent result, not unrelated diagnostics. Tickers alone do not establish identity.

Source as-of and import time are distinct. Keep dates/timezones where meaningful; a trading date is not an invented timestamp. No general bitemporal/event-ledger framework is required. Retain sources privately outside source control; hashes identify files and do not anonymize them.

SQLite is the single authority for current import/run records. Store supplied quantities/basis/entered exact amounts as decimal text and derived estimates as finite numerical values under the numerical contract. T019.3 currently implements `advisory-import-v1`, `advisory-analysis-v1` and `advisory-suggestion-v1`. Version labels identify the chosen current format and permit clear unsupported-format errors; they do not require older readers, schema migrations, export bridges or old-backup support. Breaking development changes may use an explicitly scoped fresh runtime/reimport. No exact source-code hash defines the data contract, and unsupported state must never become a silently repaired/empty portfolio.

## Records

These are logical responsibilities, not a requirement for a table/class per row. API DTOs may expose safe subsets. Pydantic checks shape, Polars handles tables and explicit domain checks handle material eligibility/financial conditions; avoid repeating the same checks at every layer.

| Record | Required content | Behavior |
| --- | --- | --- |
| ImportSnapshot | Version/ID; selected source type/name/copy/checksum; account alias/scope; source as-of and import time; normalized security/lot/position/cash rows and units; relevant row errors and exclusions | Preview then transactionally select/replace. A failed replacement preserves the old selected snapshot. Repeated UI retry does not duplicate holdings. A changed file is not automatically an incremental transaction stream. |
| Lot observation | Stable source/internal lot reference, security/account, supplied remaining decimal quantity and total adjusted basis or unknown, acquisition/term/classification facts as available | Total versus per-share basis explicit. Ambiguous identity/missing basis blocks the affected sale estimate. Fractional holdings survive whole-share proposed orders. No remaining-basis accounting ledger. |
| Profile/settings | Selected benchmark/candidate scope; explicit economic/risk limits; restrictions; selected additional cash and separate optional final target; tax scenario only if supplied | Record actual enabled/disabled options and values. No hidden investor defaults; untouched account cash is not a funding budget. |
| Screening inputs | Relevant dated activity, manual restrictions and scope/coverage assumptions, with useful source references | May inform known-conflict/conditional-history screening; never apply activity again to current holdings. No submission/monitoring state. |
| Benchmark input | Selected fund/source/date, original complete source copy, primary/alternate/subset relationships where needed, retained-equity/exclusion rows/reasons, included identities/values and derived weights | D045 marketValue/E normalization with E positive and included facts complete. Preserve exclusions/unknowns, not per-field token proof objects. Exclusions create no inferred cash. Missing/invalid included evidence blocks affected risk/suggestions. |
| History/taxonomy/quotes used | Ordered stable securities and sessions, source/date/convention/adjustment/calendar/currency, required observations/classifications, quality findings and reference mark dates | Keep the data actually used by saved runs. Compatible cache reuse and manual refresh are supported; no mixed-vintage append, silent filling or complete-coverage claim from last date alone. Current quotes and adjusted history have different uses. |
| AnalysisRun | Version/ID; input revision and snapshot reference; input window/data actually used; settings/model/application version; as-of/start/completion; status, estimated outputs, exclusions and warnings | Snapshot the inputs used and store outputs. Publish as current only if relevant input/settings revision still matches. Current-format historical viewing does not require recalculation; no cross-schema preservation promise. A new run creates new results rather than rewriting an old saved result. |
| SavedSuggestion | Version/ID and run reference; security/lot references, sides/whole-share quantities, indicative prices/costs/loss/risk/cash, assumptions/warnings, data/export dates and validation outcome | Independent final checks; edits create a new suggestion. A saved/exported worksheet is a dated estimate, not an executable order, reservation or evidence of fills. |

Derived cache rows can be rebuilt; retained saved-run inputs are user data. Retain only what saved runs need plus chosen reusable history, rather than every intermediate/failed request forever. If required bytes disappear, explain the affected unavailability without making unrelated historical output unreadable. User-visible deletion/export/retention controls are implemented deliberately; no automatic purge follows from this contract.

## Holdings-first assembly and selected cash

Current lot/holding snapshots establish the starting state. Attributable supplemental facts can resolve specific unknowns. Missing history permits conditional screening with explicit warnings/manual restrictions under D038; known conflicts and required basis/identity/risk facts retain their scoped blockers. Compare independent positions if supplied; do not demand a redundant export or assume a sum of lots independently proves source completeness.

Keep imported cash (optional), selected additional-cash budget and optional final-cash target separate. Compute stock-sleeve-plus-selected-cash baseline/final weights; untouched balances remain outside the modeled sleeve. D045 benchmark retained equities sum approximately to one under the numerical contract. Final cash/quantities are recomputed after costs and discrete choices.

## Snapshot and event reconciliation

V1 replaces selected current snapshots transactionally rather than reconstructing accounts from fills/events. Imported activity is screening information, not an instruction to add holdings already represented in the opening snapshot. Source cutoff uncertainty is reported where it affects a calculation; no fabricated same-day sequence or full account reconciliation is required to display a holding.

Correct a source value through a new import/reviewed observation while preserving saved outputs and original sources. Do not infer broker lot allocation, add a wash adjustment twice, or merge lots merely because date/ticker/price match. Actual-fill reconciliation, order status, basis maintenance and forward monitoring are deferred under D046. After external trading, require a fresh holdings/lot snapshot for another suggestion.

## Time semantics

Retain source as-of, import time, analysis as-of and relevant activity/restriction dates. Keep reference quote and historical-window dates visible. A fresh download of an old report is still old economic data. Scope/date assumptions affecting screening must be explicit, including cross-year periods where applicable. Current-format stored estimates remain readable during normal use; freshness affects their reuse. D047 permits format-breaking development changes with a documented scoped fresh runtime/reimport instead of migration.

## Generic import bundle

New advisory import shape is `advisory-import-v1` above. Selected-source adapters normalize supported spellings/notation and preserve original bytes; source/row-size and finite/magnitude checks remain. Unknowns, duplicate/ambiguous lot/security mapping and required missing fields have located explanations. Synthetic fixtures and future authorized private inputs use the same calculation contracts; synthetic labeling is not a second product lifecycle. No new API snapshot/generated TypeScript is edited by T019.1.

The old `synthetic-checkpoint-v1` transport is a superseded development implementation documented historically in [FOUNDATION_SPEC](../engineering/FOUNDATION_SPEC.md#exact-value-contract). There is no requirement to read/map/export it or retain its validators after current consumers are updated. T019.3.1 removes the newly added checkpoint bridge; .4-.7 replace remaining old implementation paths directly.

## Advisory storage and clean-start records

T019.3 implemented [advisory_records.py](../../src/prosper/advisory_records.py) and [AdvisoryStore](../../src/prosper/advisory_store.py) at a library/service boundary. `advisory-v1.sqlite3` currently owns new imports, deduplicated source BLOBs, import times, selected input/settings revision, command receipts, run inputs/outputs and unvalidated worksheet envelopes. `stage`/`snapshot`/`source` support preview; `select` and `configure` use revision checks and durable retry receipts. Failed or repeated operations must preserve current work. Imported decimal strings and explicit unknowns remain material facts, not old-format compatibility.

`start_run` freezes the selected snapshot reference, current settings and the actual supplied calculation inputs/window plus application/model versions. Use advisory estimate APIs. `complete_run` saves finite outputs/exclusions/warnings and publishes only against the relevant revision/latest started run. `catalog`/`run`/`suggestion` support current-format historical viewing without recalculation. A missing source copy reports its own error without hiding stored outputs. `SavedSuggestion` permits only `not_validated`; final suggestion validation and investor worksheet UI remain future work.

**D047 cleanup:** T019.3 also introduced `advisory_legacy.py`, a checkpoint export/mapper, and kept the old database/readers alongside the new service. This is observed unfinished cleanup, not adopted future architecture. [T019.3.1](../tasks/T019-advisory-remediation.md#t01931-remove-the-unreleased-checkpoint-bridge) removes the bridge and compatibility-only tests/examples, and establishes a clean normalized synthetic workflow. .4 replaces history/assembly paths, .5 consolidates current-format backup/restore, .6 updates API/UI consumers and generated contracts together, and .7 removes remaining redundant implementations. No old-reader/migration/export qualification blocks these tasks; no dual-store or dual-write design is required for compatibility.

Current legacy foundation/history backups do not include the new advisory database. T019.5 must provide recovery for the chosen current authoritative records before .6 UI adoption; it need not restore any superseded backup. Unsupported existing development state gets a clear error and an identified fresh-runtime/reimport route, without automatic data deletion. Historical reports retain evidence for their original candidates and impose no future compatibility guarantees. Data-provider/calendar/adjustment and dependency compatibility remain factual validity checks under D047.
