# ADR-0006: Persistent market-history cache and incremental refresh

Date: October 23, 2026 PDT / October 24 UTC; owner amendment October 24, 2026. Status: **Accepted engineering requirement; implementation and qualification pending**. Decision: D040. Approver: project owner, explicit request to cache downloaded returns and fill subsequent gaps instead of repeatedly downloading the same history, followed by adoption of the validation policy below.

## Question and context

A later portfolio review should reuse previously downloaded history. If the user returns a month later, existing securities should normally require only the intervening observations and a bounded validation overlap; new securities or a longer lookback require their missing history. Retaining only the last optimization's temporary DataFrame would lose this benefit across restarts or portfolios.

The accepted architecture already separates immutable original evidence, derived analytical data and frozen risk inputs. [T017.1's bounded evaluation](../../tasks/T017.1-free-risk-qualification.md) retains source responses locally, but it does not implement a reusable application cache or incremental refresh service. This request adopts that feature in the engineering plan; it does not start the application implementation or a new market-data download.

## Alternatives and decision

Reject full-history download for every run as the default. A memory-only cache is insufficient. A persistent append-only adjusted-price table without revision checks cannot establish a coherent return series across downloads. Adopt persistent local caching of permitted historical observations and derived returns, with coverage-aware incremental refresh and immutable run snapshots.

Requirements:

1. **Persist and reuse across sessions and portfolios.** Retain all successfully downloaded history within applicable permission/retention scope, with original response bytes and source numeric lexemes distinct from derived prices/returns. Store production data under the private application runtime, outside source control; research scratch remains ignored/local. Market-history reuse is scoped to the same local user/provider entitlement, not a shared service across users. Credentials are excluded from cache keys, URLs, manifests and logs.
2. **Identify comparable series.** Index by provider/dataset, resolved security identity and dated provider-symbol mapping, currency, calendar/timezone, observation interval, adjustment/repair conventions, schema/transform/library versions and permission scope. Keep raw/provider-reported close, adjusted close, actions and derived returns distinguishable. A ticker alone or the latest available date is not a complete identity/coverage proof.
3. **Plan missing intervals before requests.** Compare the requested universe/window/cutoff to verified cached coverage. Reuse matching observations. Fetch missing leading/tail/interior intervals and new-name history, plus only the overlap/revalidation required by the qualified provider policy. Include the preceding valid observation needed to calculate the first new return, respecting the trading calendar and provider endpoint boundary conventions. Known holidays are not missing trading sessions; an absent provider row is not automatically a holiday. Record requested, received and usable coverage separately; partial/empty/error responses never advance a false complete watermark.
4. **Handle revisions and adjustment vintages.** Splits, dividends, repairs and provider corrections can change older adjusted observations. Do not blindly append newly adjusted prices to a different vintage. Compare overlap and action metadata; use a qualified coherent adjustment reconstruction or expand the refetch/revalidation range when necessary. An unchanged overlap does not prove all earlier dates are unrevised. Provide broader historical validation under the owner-amended policy below, with scheduled execution **Never / Off by default** and future user opt-in; provider evidence determines supported ranges/cadences. Retain superseded versions and invalidate/recompute dependent derived returns/models rather than overwrite a frozen run. Full-window refetch is an explicit justified exception, not the normal refresh path. Exact overlap/cadence settings remain implementation/data qualification work under D012/D017.
5. **Publish safely and preserve unknowns.** Verify source identity, hash, schema, boundaries, duplicates and values before publishing a new usable cache version. Interrupted/repeated/concurrent refreshes must not corrupt prior usable data, duplicate rows or silently replace a newer observation version. Retain failures and unresolved gaps; do not forward-fill invented zero returns, mix incompatible adjustment conventions, drop missing names or normalize away missing benchmark weight. A gap only blocks computations that require it; older complete snapshots remain available with their original cutoff.
6. **Freeze each analysis.** Build the risk model from a named immutable history version/manifest, exact source references, selected date window/cutoff, ordered universe, transformations and estimator settings. Updating the cache creates a new input version; it does not change old model/plan results. Previously used input evidence remains required recovery material even if a generic cache can otherwise be rebuilt. Eviction/permission expiry must respect those dependencies or explicitly mark affected replay unavailable; a backup cannot confer retention rights.
7. **Make freshness and operation clear.** Show last usable history date, last successful refresh, last successful broader validation (or Never), unresolved coverage and refresh outcome. Repeated runs with complete matching coverage perform no redundant history download unless a qualified refresh/revalidation condition requires one. Offline use may reuse a complete retained snapshot with its cutoff visible; it cannot label stale data current or bypass actionable-plan freshness checks. Updating history and recomputing covariance does not itself refresh execution/reference quotes. Scheduled broader validation is an optional future feature, disabled by default under the amendment below; no schedule or startup network job is activated by this documentation. Unlimited disk retention, eviction implementation and new provider entitlement remain unselected.

Provider-specific revision risk is concrete: the official [yfinance repair documentation](https://ranaroussi.github.io/yfinance/advanced/price_repair.html), checked October 24 UTC, describes missing split/dividend adjustments, provider corrections and changes between reconstructed and subsequently fixed source values. Those observations justify revision-aware design; they do not select automatic repair or prove that a short overlap catches every revision.

## Owner amendment: validation and optional scheduling

On October 24, 2026, the owner adopted the proposed automatic overlap checks, targeted refresh on detected changes, broader historical validation and manual refresh controls, with the explicit modification: **make the default setting to never be scheduled for run, and allow a future user to toggle the feature on**. This refines D040; it does not implement the cache, activate a job or change the current next-task sequence.

- **Ordinary requested refresh:** fetch missing dates with qualified boundary/overlap observations and compare comparable price/return observations, actions and identity/convention metadata. Calculate the first new return from adjacent valid observations in the new response. A new response hash alone is not evidence of an economic revision. A common price rescaling need not change historical returns; qualify the reconciliation rule before relying on it, including consistent OHLC/action inputs. An unchanged overlap cannot establish that older history is unchanged.
- **Detected discrepancy:** reconcile changed observations/actions and provider, identity, mapping, adjustment/repair or transformation-version changes. If consistency cannot be established, refetch/revalidate the affected security's full required model window and rebuild affected returns/risk inputs before dependent use. Keep unsupported or failed combinations unavailable rather than treating the newest response as proof of correctness. Preserve original source bytes and frozen old runs.
- **Optional scheduled broader validation:** provide a persistent user setting displayed as **Scheduled historical validation: Off**, with schedule **Never** as the initial/default state. In that state, perform no timer-driven validation fetch, startup catch-up or overdue scheduled run, across restarts. A future user may explicitly enable the feature and select a supported, qualified cadence and scope; exact enabled choices remain implementation/provider qualification. Turning it off prevents future scheduled dispatch and preserves the cache and past validation evidence. No operating-system service, wake-up behavior or background-runtime dependency is selected by this amendment.
- **Separate controls:** scheduled broader validation being Off does not disable overlap/action checks during an explicitly requested refresh, targeted refresh needed to resolve a detected discrepancy, or manual refresh. Offer manual refresh for selected securities and for all required securities over the required analysis lookback; a wider retained-history refresh can be an explicit scope choice. Do not automatically reload all retained history for every run or silently enable scheduling because the user requests a manual refresh.
- **Visible limits:** show the scheduled setting, validation scope, last successful broader historical-validation time or **Never**, and unresolved differences/failures. With scheduling Off, an older correction outside fetched ranges may remain undetected until manual or otherwise explicitly triggered broader validation. A recent tail refresh is not a completed full-window validation. Disabling scheduling does not make stale, missing or unqualified inputs acceptable or bypass existing actionable-plan freshness checks.

Implementation ownership remains T006.1 for cache/revalidation policy and persistence, T006.2 for version-dependent return/model recomputation, T008 for the investor-facing setting/manual controls, and T018/recovery for lifecycle/concurrency and retained-input integrity. The [completed offline experiment](../../tasks/T017.1.3-history-refresh.md) establishes mechanics/refusal only; live revision coherence and the numerical reconciliation rules remain unqualified. This amendment adopts the feature and its disabled default, not an exact overlap, cadence, freshness limit, yfinance repair mode or provider revision guarantee.
